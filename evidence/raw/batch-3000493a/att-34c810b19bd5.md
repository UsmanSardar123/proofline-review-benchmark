### Summary of Changes
The proposed changes modify the `history` function in `reports.py` to order the delivery reports by `scheduled_at` in descending order, and then by `id` in descending order. This change aims to show the most recently scheduled deliveries first. Additionally, it updates the logic for determining the `next_cursor` to use the `scheduled_at` field instead of the `id`.

### Critical Issues and Findings

1. **Logic Bug in Cursor Handling**:
   - **File**: `reports.py`
   - **Line**: `+    next_cursor = rows[limit - 1][2] if len(rows) > limit else None`
   - **Issue**: The `next_cursor` is now set to the `scheduled_at` field of the last row fetched. However, this can lead to incorrect pagination behavior if there are multiple deliveries with the same `scheduled_at` timestamp. The cursor should uniquely identify the position in the dataset, and using only `scheduled_at` does not guarantee uniqueness.

2. **Potential Data Integrity Defect**:
   - **File**: `reports.py`
   - **Line**: `+        query += " WHERE scheduled_at < ?"`
   - **Issue**: If the `scheduled_at` field is not unique, the query might skip some records or include duplicates when fetching the next page. This could lead to data integrity issues where some deliveries are missed or repeated in the report history.

3. **Regression Risk**:
   - **File**: `reports.py`
   - **Lines**: `+        query += " ORDER BY scheduled_at DESC, id DESC LIMIT ?"`
   - **Issue**: The original ordering was by `id`, which ensured a consistent and predictable order of records. Changing the primary sort key to `scheduled_at` could introduce regressions if the application relies on the `id` order for other functionalities.
