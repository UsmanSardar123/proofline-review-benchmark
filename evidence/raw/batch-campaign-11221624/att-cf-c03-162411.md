### Summary of Changes
The proposed changes aim to optimize the `deliver_due` function by batching the database operations. Instead of executing individual `INSERT` and `UPDATE` statements for each job, it groups them into batches of 20 to reduce the overhead associated with setting up multiple database statements.

### Critical Issues and Findings

1. **Logic Bug in Loop Range (reports.py, Line 78)**
   - **Issue**: The loop range `range(0, len(jobs) - batch_size + 1, batch_size)` can cause the last few jobs to be skipped if the total number of jobs is not a perfect multiple of the batch size.
   - **Explanation**: If `len(jobs)` is not a multiple of `batch_size`, the last batch will not be processed because the loop stops before reaching it. For example, if there are 21 jobs, the loop will only process the first 20 jobs, and the 21st job will be ignored.

2. **Data Integrity Defect (reports.py, Lines 82-85)**
   - **Issue**: There is no transaction management around the batch operations, which could lead to partial updates if an error occurs during the batch processing.
   - **Explanation**: If an error occurs after some but not all jobs in a batch have been processed, the database might end up in an inconsistent state where some deliveries are marked as delivered but their corresponding receipts are not created, or vice versa.

3. **Operational Risk (reports.py, Lines 82-85)**
   - **Issue**: The batch size is hardcoded to 20, which may not be optimal for all scenarios.
   - **Explanation**: The optimal batch size can vary based on the database system, the network latency, and the specific workload. A one-size-fits-all approach might not be efficient in all cases.

4. **Performance Bottleneck (reports.py, Lines 82-85)**
   - **Issue**: The use of `executemany` without considering the database's ability to handle large batches can lead to performance issues.
   - **Explanation**: While `executemany` is generally more efficient than executing individual statements, very large batches can cause memory issues or lock contention in the database, leading to performance degradation.

### Recommendations and Suggested Fixes

1. **Fix the Loop Range (reports.py, Line 78)**
   - **Recommendation**: Change the loop range to ensure all jobs are processed.
   - **Suggested Fix**:
     ```python
     for start in range(0, len(jobs), batch_size):
         batch = jobs[start:start + batch_size]
         # ... rest of the batch processing code ...
     ```

2. **Add Transaction Management (reports.py, Lines 82-85)**
   - **Recommendation**: Use transactions to ensure atomicity of batch operations.
   - **Suggested Fix**:
     ```python
     processed = 0
     batch_size = 20
     for start in range(0, len(jobs), batch_size):
         batch = jobs[start:start + batch_size]
         try:
             db.execute('BEGIN TRANSACTION')
             db.executemany(
                 "INSERT INTO receipts VALUES (?, ?)",
                 ((job_id, now) for (job_id,) in batch),
             )
             db.executemany(
                 "UPDATE deliveries SET delivered_at = ? WHERE id = ?",
                 ((now, job_id) for (job_id,) in batch),
             )
             db.execute('COMMIT')
             processed += len(batch)
         except Exception as e:
             db.execute('ROLLBACK')
             raise e
     ```
